# mubuagent

`mubuagent` 是一个基于 FastAPI 的智能聊天机器人服务，支持普通 LLM 对话、本地知识库 RAG 检索、Tool Calling、多轮 Agent 循环、复杂任务规划以及知识库回答的事实支撑度校验。

系统会根据用户问题自动判断是否需要调用工具：普通问题由 LLM 直接回答；涉及本地知识库、项目文档或私有资料的问题，会先调用知识库检索工具获取上下文，再由 LLM 基于检索结果生成最终回答，并对知识库回答进行语义支撑度校验，提示潜在幻觉风险。

项目适合用于个人或企业的本地知识库助手、项目文档问答、智能客服原型，以及 RAG、Tool Calling、Agent Loop、Prompt 分层设计等应用实验。

## 功能特性

- **普通 LLM 对话**：支持通用聊天、问答、总结、解释等常规大模型能力。
- **Prompt 分层设计**：按基础身份、全局行为、工具使用、任务规划、知识库规则和回答生成等层级组织系统 Prompt。
- **知识库工具调用**：当问题涉及本地文档或项目资料时，由大模型自动调用知识库检索工具。
- **LLM 生成检索回答**：知识库工具只返回相关上下文，最终答案由 LLM 进行理解、筛选、归纳和生成。
- **本地知识库检索**：支持对本地文档构建索引，并通过混合检索获取相关内容。
- **事实一致性校验**：对知识库回答与检索上下文进行语义支撑度计算，返回风险等级和支撑分数。
- **Agent 循环结构**：支持 LLM 与工具的多轮交互，直到生成最终回答或达到最大执行轮次。
- **TodoWrite 任务规划工具**：复杂任务中可创建或更新任务计划，展示当前执行步骤和进度。
- **多轮会话能力**：支持会话历史保存，并在上下文过长时进行压缩。
- **Web 聊天界面**：内置网页端聊天入口，可直接在浏览器中使用。
- **索引重建接口**：支持通过页面按钮或 API 重新构建知识库索引。

## 工作方式

系统收到用户消息后，由 `ChatBot` 统一处理。系统先加载会话历史，再由 `MessageBuilder` 构建包含分层 Prompt、历史消息和用户问题的 messages，并交给 LLM 判断是否需要调用工具。

如果 LLM 不需要工具，则直接生成最终回答；如果需要工具，则进入 Agent 循环：LLM 产生工具调用请求，系统执行工具，将工具结果写回 messages，再次交给 LLM 继续推理或生成最终回答。

当调用知识库工具时，工具只返回相关文档片段，最终答案仍由 LLM 基于检索上下文生成。生成完成后，系统会对知识库回答和检索上下文进行语义支撑度校验，并保存会话历史。

```text
用户提问
  ↓
FastAPI 聊天接口
  ↓
ChatBot 加载会话历史
  ↓
上下文压缩（必要时）
  ↓
MessageBuilder 构建分层 Prompt 和 messages
  ↓
LLM 判断是否需要调用工具
  ├─ 不需要工具：直接生成最终回答
  └─ 需要工具：进入 Agent 循环
        ↓
      执行工具
        ↓
      工具结果写回 messages
        ↓
      LLM 继续推理或生成最终回答
  ↓
知识库回答执行事实支撑度校验
  ↓
保存多轮会话历史
  ↓
返回最终回复
```

Agent 循环具有最大轮次限制，当前默认最大循环轮次为 `max_loops=6`，用于避免工具调用陷入无限循环。

## Prompt 分层设计

项目中的系统 Prompt 由 `chatbot_agent/message_builder.py` 中的 `MessageBuilder` 统一构建，采用分层结构组织行为约束：

1. **基础身份层**：定义助手角色，以及判断是否调用工具和生成最终回答的基本职责。
2. **全局行为规则**：规定中文回复、多轮对话、信息不足时追问、不编造信息等行为。
3. **工具使用规则**：规定工具调用条件、参数不足时的处理方式，以及工具失败或结果不足时的处理方式。
4. **规划工具规则**：规定复杂任务使用 `todo_write` 制定计划，并管理 `pending`、`in_progress`、`completed` 状态。
5. **知识库工具专用规则**：要求严格基于知识库上下文回答，并在回答末尾列出来源。
6. **回答生成规则**：默认采用“结论 + 依据/说明 + 步骤或注意事项 + 来源”的结构。

这种设计避免所有规则混杂在一个长 Prompt 中，便于维护，也便于后续扩展联网搜索、数据库查询、文件分析等工具。

## Agent 循环与工具调用

项目采用循环式 Agent 执行结构，而不是简单地“调用工具后直接返回工具结果”：

1. LLM 接收当前 messages，判断是否需要调用工具。
2. 没有工具调用时，直接返回 LLM 生成的最终回答。
3. 存在工具调用时，系统执行对应工具。
4. 工具结果以 `tool` message 的形式追加到 messages。
5. LLM 读取包含工具结果的 messages，继续调用工具或生成最终回答。
6. 达到最大循环轮次时停止循环并返回结果。

该结构支持先规划任务、再检索知识库，也支持多次调用工具补充上下文。工具调用由 `LLMClient` 负责请求和响应封装，工具执行由工具执行器负责。

## TodoWrite 任务规划工具

项目内置 `todo_write` 工具，用于复杂任务的计划制定和进度更新。它适用于多步骤、跨文件、需要多个工具或复杂分析的任务。

每个任务项包含：

- `content`：任务内容。
- `status`：任务状态，只能为 `pending`、`in_progress` 或 `completed`。
- `session_id`：可选的会话 ID，用于区分不同会话的计划。

`todo_write` 只负责记录计划和展示进度，不执行具体任务。简单问答、闲聊和单次知识库检索通常不需要调用该工具。

## LLM 生成检索回答

知识库检索工具只负责根据问题返回相关文档片段，不直接决定最终答案。工具执行完成后，系统会将检索结果作为上下文重新提供给 LLM，由 LLM：

- 判断哪些片段与问题真正相关；
- 对检索内容进行归纳和组织；
- 避免直接堆砌原文片段；
- 生成结构清晰的最终回答；
- 在回答末尾列出使用到的来源。

知识库问答遵循严格基于上下文的原则。如果检索上下文中没有足够信息，应明确说明“知识库中没有找到相关内容”，而不是使用模型自身知识补充或编造。

## 事实一致性校验

当回答来源为知识库时，系统会对最终回答和知识库检索上下文进行语义相似度计算，用于估计回答是否得到检索内容支撑。

校验结果记录在 `fact_check` 字段中，主要包括：

- `risk`：风险等级，通常包括 `low`、`medium` 和 `high`。
- `support_score`：语义支撑分数，取值范围约为 `0.0` 到 `1.0`。

该校验是基于 embedding 相似度的风险提示机制，不等价于严格的事实证明。当回答与检索上下文的支撑度较低时，系统会提示用户结合来源内容进行核对。

## 项目结构

```text
mubuagent/
├── app.py                         # FastAPI 服务入口、网页界面和 API
├── config.py                      # 项目配置、路径与环境变量管理
├── core_rag.py                    # 本地知识库检索、混合搜索与索引构建
├── chatbot_agent/                 # 聊天机器人核心模块
│   ├── chatbot_agent.py           # ChatBot 主逻辑、Agent 循环和事实校验
│   ├── agent_config.py            # Agent 配置加载与校验
│   ├── llm_client.py              # 大模型客户端封装和 Tool Calling
│   ├── message_builder.py         # 消息与分层 Prompt 构建
│   ├── session_manager.py         # 会话历史管理与上下文压缩
│   ├── tool_decorator.py          # 工具注册装饰器
│   ├── tool_executor.py           # 工具执行器
│   └── Tools/                     # 内置工具目录
│       └── todo_write_tool.py     # TodoWrite 任务规划工具
├── utils/                         # 日志、模型请求结构等工具函数
├── data/                          # 索引、缓存和运行数据
└── 知识库/                         # 默认本地知识库目录
```

## API 接口

### 健康检查

```http
GET /api/health
```

返回服务状态。

### 聊天接口

```http
POST /api/chat
```

请求示例：

```json
{
  "session_id": "web_chat",
  "message": "项目里的知识库工具怎么用？"
}
```

响应示例：

```json
{
  "answer": "知识库工具的使用方式是...",
  "source": "knowledge_base",
  "contexts": [
    {
      "title_path": "项目说明 / 工具调用",
      "source_file": "项目说明.md",
      "content": "..."
    }
  ],
  "tool_results": [
    {
      "role": "tool",
      "tool_call_id": "call_xxx",
      "content": "..."
    }
  ],
  "fact_check": {
    "risk": "low",
    "support_score": 0.5342
  },
  "hallucination_risk": null,
  "support_score": null
}
```

字段说明：

- `answer`：最终回答内容。
- `source`：回答来源。`llm` 表示 LLM 直接回答，`knowledge_base` 表示调用知识库工具后由 LLM 生成回答。
- `contexts`：知识库检索返回的相关片段，用于展示来源。
- `tool_results`：Agent 工具调用结果。
- `fact_check`：知识库回答的事实支撑度校验结果。
- `hallucination_risk`：幻觉风险预留字段。
- `support_score`：支撑分数预留字段。

### 重建知识库索引

```http
POST /api/rebuild
```

用于重新扫描知识库目录并构建索引。

响应示例：

```json
{
  "document_count": 128,
  "message": "索引重建成功"
}
```

## 配置说明

项目通过 `.env` 文件和 `config.py`、`agent_config.py` 管理配置。使用前需要配置大模型 API Key、接口地址和模型名称；如需更换知识库目录，也可以通过环境变量指定本地文档路径。

主要配置包括：

- 大模型 API Key、接口地址和模型名称；
- 温度参数；
- 会话历史 token 窗口、历史压缩比例和保留轮数；
- 知识库目录；
- 索引与缓存目录；
- Agent 最大循环轮次。

知识库检索、文档切片和召回数量等参数已经提供默认值，一般情况下无需修改。首次运行时，只需要准备好大模型 API Key，并将需要检索的文档放入默认知识库目录即可。

## 快速开始

### 1. 安装依赖

根据项目依赖安装 Python 运行环境。核心依赖包括：

- `fastapi`
- `uvicorn`
- `pydantic`
- `python-dotenv`
- `openai`
- `chromadb`
- `rank_bm25`
- `numpy`
- `requests`
- `loguru`

### 2. 配置环境变量

在项目根目录创建 `.env` 文件，并配置大模型接口信息。

### 3. 准备知识库文档

将需要检索的文档放入 `知识库/` 目录，或通过 `DOC_DIR` 指定其他目录。

### 4. 启动服务

```bash
uvicorn app:app --reload
```

浏览器访问：

```text
http://127.0.0.1:8000
```

### 5. 构建知识库索引

首次使用或文档更新后，需要重建索引：

- 在 Web 页面点击“重建知识库索引”按钮；
- 或调用 `POST /api/rebuild`。

## 总结

`mubuagent` 当前已经从简单的知识库问答服务升级为具备 Prompt 分层、Tool Calling、Agent 循环、任务规划、RAG 回答生成和事实支撑度校验能力的智能聊天机器人原型。它既可以处理普通 LLM 对话，也可以在需要时调用本地知识库工具，并基于检索结果生成带来源依据的回答。
